# Система мониторинга ресурсов

## Цель и согласованные решения

- Реализовать `resi/res_sender.lua` для компьютеров рядом с хранилищами и `resi/res_display.lua` для главного компьютера с монитором.
- Каждый sender автоматически обнаруживает все подключенные периферии типа inventory и суммирует содержимое по item ID.
- Sender также читает поддерживаемые fluid tanks и передает жидкости отдельно от предметов.
- Связь выполняется через wireless modem по общему настраиваемому каналу, например `4820`, с отдельным `protocol` для защиты от сообщений других программ.
- Все sender передают полные периодические снимки. Display агрегирует одинаковые item/fluid ID в общий итог.
- На display основной режим показывает общий итог, режим источников показывает данные конкретных sender. Имя sender задается в его `CONFIG`.
- Монитор автоматически листает страницы; касания кнопок `PREV`, `NEXT` и `SOURCES/TOTAL` меняют страницу или режим.

## Протокол и модель данных

1. В обоих файлах определить одинаковые настройки `modemSide`, `channel`, `protocol` и интервалы обновления. У sender добавить `sourceName`, у display добавить `monitorSide` и параметры автопрокрутки.
2. Sender отправляет таблицу, сериализованную через `textutils.serialize`, примерно следующей формы:
   - `protocol`, `type = "snapshot"`, `source`, `computerId`, `sentAt`;
   - `items`, где ключом является точный item ID, а значением количество;
   - `fluids`, где ключом является точный fluid ID, а значением количество и, если доступно, единица измерения.
3. Display принимает только сообщения с правильными `protocol` и `type`, проверяет типы полей, а некорректные сообщения игнорирует без падения программы.
4. Display хранит последний снимок по `computerId` или source, время приема и статус. Источник считается offline/stale, если снимок старше заданного TTL; его данные не включать в общий итог, но показывать в подробностях как устаревшие.

## Реализация sender

1. Проверить наличие wireless modem с `transmit`, открыть общий канал и вывести понятную ошибку при отсутствии модема.
2. Каждый цикл получать `peripheral.getNames()` и для каждого имени безопасно вызывать `peripheral.getType`/`peripheral.wrap` через `pcall`, чтобы отключение устройства не завершало программу.
3. Для периферий с методом `list` пройти все слоты и суммировать `item.name` и `item.count`; не ограничиваться первым слотом и не смешивать разные item ID с одинаковым отображаемым названием.
4. Для периферий с tank API безопасно получить содержимое через доступный в CC:Tweaked метод `tanks`/`getTanks` и суммировать идентификатор жидкости и количество. Нормализовать различия API в одну внутреннюю структуру; недоступные методы считать отсутствием этого типа данных, а не критической ошибкой.
5. Отправлять полный снимок по таймеру с `modem.transmit(channel, channel, serializedMessage)`. Устранить дублирование одной и той же peripheral, если она появляется в нескольких категориях.
6. Перерисовывать краткий диагностический статус на терминале: число найденных inventory/tanks, время последней отправки и текст последней ошибки. При временном исчезновении периферии продолжать цикл.

## Реализация display

1. Проверить монитор и wireless modem, открыть канал, настроить `setTextScale`, палитру и адаптивные размеры. Все строки обрезать по ширине монитора, чтобы маленький монитор не вызывал ошибки позиционирования.
2. На каждом `modem_message` разобрать snapshot и обновить состояние источника. Не принимать данные с неправильным протоколом или невалидными счетчиками.
3. Построить общий список ресурсов:
   - суммировать только свежие снимки;
   - отдельно хранить items и fluids;
   - сортировать по количеству по убыванию, затем по ID;
   - форматировать большие значения компактно (`1.2k`, `3.4M`) с возможностью показать точное число в строке, если хватает места.
4. Построить список источников для подробного режима: source name, online/stale статус, количество найденных типов и страницы его ресурсов. Для отсутствующих источников показывать последнее имя и время последнего сообщения.
5. Разбить строки на страницы по фактической высоте монитора. Заголовок должен содержать название панели, режим, номер страницы и число активных источников; строки должны визуально различать items и fluids, а stale/error состояния выделять цветом.
6. Добавить нижнюю панель управления с областями касания:
   - `PREV` и `NEXT` листают страницы;
   - `TOTAL`/`SOURCES` переключает общий и подробный режим;
   - при слишком узком мониторе использовать сокращенные подписи и равномерно разделять доступную ширину.
7. Использовать один таймер для обновления экрана и автопрокрутки, другой при необходимости для stale-очистки; одновременно обрабатывать `modem_message`, `monitor_touch`, `timer` и `term_resize` в основном цикле.
8. Если sender еще не подключился, вывести красивый пустой экран с инструкцией проверить modem/channel, а не пустой монитор или ошибку Lua.

## Краевые случаи и ограничения

- Один sender может иметь несколько inventory и tanks; ресурсы из них объединяются внутри его snapshot.
- Два sender с одинаковым `sourceName` не должны терять данные: ключом состояния остается computer ID, а имя отображается с коротким ID при конфликте.
- Переполнение/нечисловые значения, поврежденная сериализация и слишком длинные ID должны безопасно обрабатываться.
- Снимок может прийти несколько раз; display должен просто заменить состояние источника, а не удваивать его.
- При перезапуске display состояние очищается и восстанавливается следующими снимками; sender не требует ручного запроса.
- При остановке sender не требуется удаленная команда; display помечает его stale после TTL.
- Fluid API конкретного мода может отличаться. Реализовать безопасный адаптер для стандартного CC:Tweaked tank API и явно показывать неподдерживаемые tanks в диагностике, не смешивая жидкость с предметами.

## Проверка

1. Запустить sender с одним и несколькими inventory, проверить суммирование одинаковых item ID по слотам и перифериям.
2. Изменить содержимое хранилища и убедиться, что следующий snapshot отражает новое количество без удвоения.
3. Подключить tank, проверить отдельный раздел fluids и корректную единицу количества; отключить tank и убедиться, что sender продолжает работу.
4. Запустить несколько sender с разными именами, проверить общий итог и отсутствие смешивания по источникам.
5. Остановить один sender и проверить переход в stale/offline после TTL, а также исключение устаревших данных из общего итога.
6. Проверить страницы, автопрокрутку, касания трех кнопок и изменение размеров монитора на малом и большом мониторе.
7. Отправить неправильную сериализацию, другой protocol и поврежденные поля; display должен игнорировать сообщения без остановки.
8. Проверить отсутствие modem/monitor и временное отключение peripheral: должны отображаться диагностические сообщения, а главный цикл должен продолжать работу там, где это возможно.
